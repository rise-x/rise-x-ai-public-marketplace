# Rise-X MCP Server Skill

For background on Rise-X, the EOP platform, value proposition, and target industries, see `references/about-rise-x.md`.

## Domain Model

**Two-tier setup:**
- **Deployment** (dev/test/prod) — fixed at MCP server startup, determines API URL
- **Ecosystem** (workspace name like `MyEcosystem`) — set per-session, determines data scope. An ecosystem is a collection of workflows, work items, assets, and users with access controls for collaboration.

**Entity hierarchy:**
```
Flow (workflow template)
  -> Steps (high-level phases — Kanban columns, e.g. "Order Request", "Fulfilment")
     -> Tasks (discrete units of work assigned to specific parties)
        -> Layout (UI form definition)
           -> Sections (logical groupings of fields)
              -> Components (form fields — text, dates, signatures, etc.)
```

- **Work Item** = running instance of a flow (a live transaction). Created with `create_work(flow_id)`, progresses through steps via `submit_work`. After each task, the platform automatically notifies the party responsible for the next task.
- **Asset Type** (ThingType) = a **template** that defines the structure and fields for a category of entities. Think of it as a *class* or *schema*. Example: a "Vessel" asset type defines fields like IMO number, flag state, tonnage. Under the hood, an asset type is a Flow with `FlowResourceType = Entity`. Created with `create_flow(flow_resource_type="Entity")`, configured with flow/layout/component tools, then published.
- **Asset** (Thing / entity instance) = a **record** created from an asset type. Think of it as an *instance* of the class. Example: "Pacific Explorer" is a Vessel asset with IMO 9876543. Created/edited via the 3-step workflow pattern (`create_asset` → `update_work_data` → `submit_work`).
- **Activities** = workflow automations that run when an action fires (e.g. `StartWork`, `StartCrossEcosystemWork`, `PublishData`, `SendEmail`). They hang off an **action**, configured with `manage_activity` (add/update/delete); discover types + schemas via `get_schema("activities")`. See `references/actions-and-statuses.md` § Activities.

## Multi-Party Workflow Design (Summary)

Rise-X workflows are **multi-party permissioned forms** — each task is a handover between parties. The golden rule: **never create consecutive tasks for the same party** — use sections within one task instead. After each task, the next party is automatically notified.

For the full design guide with examples, component selection strategy, and asset flow patterns, see `references/building-workflows.md`.

Before any operation, always:
1. `get_active_ecosystem()` — check if ecosystem is set
2. If null: `list_ecosystems()` then `set_active_ecosystem("name")`
3. Every tool except session tools requires an active ecosystem

## Response Envelopes & Verification (server ≥ Trust & Signal release)

Every mutation tool returns a compact YAML **envelope** instead of echoing the
full entity:

```yaml
ok: true|false
action: <tool name>
entity: flow|layout|component|work|asset|dashboard|integration|…
id: <primary id>                  # e.g. the DRAFT id for create_*_draft
ids: {flowOriginId: …, draftId: …, layoutId: …}   # ids for follow-up calls
…summary fields…                  # added components, steps, status, context
changed: [keys confirmed applied] # PATCH-style tools
counts: {requested: N, persisted: M}
warnings: [{code, path, message}] # ← READ THIS EVERY TIME
hint: <one-liner>
error: {code, message, hint}      # failures (code like http_403, validation)
```

**Rules:**
1. **Always check `warnings[]` after every mutation.** The API silently drops
   unknown properties (200 OK, nothing persisted); the server now diffs your
   request against the saved entity and reports drops as
   `dropped_property` / `dropped_item` / `component_missing`. A warning means
   that part of your request did NOT land — do not report success to the user.
2. `value_differs` warnings are informational (server-side normalisation).
3. Need the raw payload? Pass `response_format="full"` — it arrives under
   `result:` with the warnings still attached.
4. Error envelopes carry a `code` (`http_403`, `validation`, `transient`, …)
   and usually a `hint` with the fix. A **request-side** `validation` error
   (caught before sending) means nothing was sent — fix and retry. An
   **API-side** 4xx can still *partially* persist (see the `add_components`
   partial-failure pitfall and the attachments-column "400 that commits"): when
   a write error is ambiguous, follow the hint and verify the target entity
   (`get_layout` / `get_work`) before assuming nothing changed.
5. Paginated lists (`list_work`, `list_assets`) return
   `{items: […], returned, skip, limit, hasMore, nextSkip}` — pass `nextSkip`
   as `skip` for the next page.

## Draft/Publish Lifecycle

### Editing a published flow or asset type:
1. `create_flow_draft(original_id)` → envelope `id` is the draft flow ID
2. `get_flow_steps(draft_flow_id)` → get layoutId
3. Check if layout needs drafting:
   - `get_layout(layoutId, format="summary")` → check `publishStatus`
   - If **"Published"** → `create_layout_draft(layoutId, draft_flow_id)` → envelope `id` is the draft layout ID and `sections` carries the section GUIDs. Use the draft ID for all component operations.
   - If **"Draft"** → use the layoutId as-is
4. Edit components on the (draft) layout ID
5. `publish_flow(draft_flow_id)` → publishes flow AND all linked layouts; returns the new published id + `ids.flowOriginId`

### Creating a new flow:
1. `create_flow(...)` → flow + layouts already in draft mode; response carries the steps with layout ids
2. `add_step(...)` → response includes `newStep.defaultSectionId` — pass it straight to `add_components` as `parent_section_id` (no `get_layout` round-trip)
3. Edit components directly
4. `publish_flow(flow_id)`

**Do NOT** call `publish_layout` — it does not exist. `publish_flow` handles layout publishing automatically.

**Draft ID Rule:** `create_flow_draft` returns a new draft flow ID, and `create_layout_draft` returns a new draft layout ID. Use these draft IDs for all subsequent edits and publish — the original IDs are read-only and respond with 403 Forbidden.

## Component Type Names

The server validates component types on every write: known-wrong names
(`select`→`input-select`, `rich-text`/`textarea`→`richtext-input`,
`location`→`input-location`, `timesheet`→`timesheet-table`,
`datepicker`→`date-picker`, `text-input`→`input-text`, `checkbox`→`check-box`,
`step-slider`→`step-slider-v1`, `comments`→`comments-box`, …) are **rejected
with the canonical name** before anything is sent, and unknown types produce a
warning. Canonical names you'll use most: `input-text`, `input-select`,
`richtext-input`, `date-picker`, `check-box`, `relatedWork-select` (camelCase W),
`input-location`, `timesheet-table`, `product-toggle-switch`, `data-grid`,
`attachments`, `comments-box`, `search-things`, `section`. Full list:
`get_schema("components")`.

**There is no `input-number`.** A numeric field is `input-text` with
`properties.inputType: "number"` — the server auto-corrects `input-number` (and
`number`) to that for you. Valid `inputType` values: `text` (default),
`number`, `password`, `link` (NOT `email`).

## Common Pitfalls

1. *(retired — the server returns a structured `no_ecosystem` error envelope; run the Pre-Flight Checklist.)*
2. **Forgot to draft** — editing a published flow/layout without `create_flow_draft`/`create_layout_draft` fails
3. **Forgot to publish** — changes stay invisible until `publish_flow` is called
4. **Asset 3-step pattern** — `create_asset` returns a workId; must call `update_work_data` then `submit_work`
5. *(retired — the server rejects orphan components pre-flight with a clear validation error.)*
6. **`replace_section_components` is destructive** — omitted components are permanently deleted
7. **ID confusion** — `flowOriginId` (asset type) vs `assetId` (flow ID) vs `entityId` (instance) vs `workId` (draft)
8. **Using original IDs after drafting** — `create_flow_draft` and `create_layout_draft` return NEW draft IDs. Using the original IDs for edits or publish returns 403 Forbidden. Always capture and use the draft IDs.
9. *(retired — wrong component type names are rejected server-side with the canonical suggestion.)*
10. **Always check layout publishStatus before editing** — After `create_flow_draft`, the layout referenced by steps may still be Published (if a stale draft was returned). Always check via `get_layout` and call `create_layout_draft(layoutId, draftFlowId)` if the layout is Published. **But if it is already `Draft`** (the normal case — `create_flow_draft` clones step layouts as editable drafts), edit that layout id **directly**. Calling `create_layout_draft` on an already-`Draft` step layout spawns a *detached* draft the step never points to, so `publish_flow` silently republishes the unchanged layout and your edits vanish (the publish envelope still lists the old layout id). After publishing, re-fetch the live layout (`get_layout(stepLayoutId, format="components")`) and confirm your change is actually present.
11. **Do NOT call `create_layout_draft` on new flows** — When building a new flow with `create_flow`, layouts are already in draft mode. Calling `create_layout_draft` creates orphan drafts that are disconnected from the flow.
12. *(retired — see §Component Type Names; aliases are validated server-side.)*
13. **User-invitation default is `"initiator"`** — resolved at runtime to the work initiator/task assignee. (`"@me"` does not exist; the server warns if you send it.)
14. **Confusing asset type with asset** — An **asset type** is a template/schema (e.g. "Vessel") created with `create_flow(flow_resource_type="Entity")`; an **asset** is a record/instance (e.g. "Pacific Explorer") created with `create_asset(flow_origin_id)`. Use flow tools for asset types, asset tools for asset instances.
15. *(retired — object options and `selectOptions` are rejected server-side before sending.)*
16. **`add_components` partial failure** — a failed batch may have partially landed. The error envelope lists the attempted `componentIds`: check the layout for exactly those ids and `delete_components` any that were created before retrying.
17. **Transient connection errors** — API calls may fail with "Cannot connect to host" errors. Simply retry the same call.
18. *(retired — `manage_action` rejects deprecated routing with the fix; use `ByStepName` + camelCase step name.)*
19. *(retired — the server auto-corrects `dateRange` → `showRange` and reports the fix as a warning.)*
20. **Always set `$.displayName` on new assets** — The UI list/grid shows the asset by `$.displayName`. If you only set domain fields (e.g. `$.legalEntityName`), the row appears blank. Set `$.displayName` as the first update_work_data call after `create_asset`.
21. **Asset submit uses the values create_asset returns** — `create_asset`/`edit_asset` now resolve the REAL embedded step name (e.g. `SubmitUntitledStep/Generated-...`), the available `steps`, and the `invitation` payload. Pass the returned `stepName`/`eventName`/`invitation` to `submit_work` verbatim. If `eventName` is absent from the response, call `get_work(workId)` to discover the actions — never guess `"Submit"`. Some asset flows need a second submit (`ActionSet_1`) to reach Complete — check the returned `steps` list.
22. **Asset `update_work_data` calls need `section_name` and must run sequentially** — Asset type flows have a single task (e.g. `UntitledTask/Generated-...`). Pass it as `section_name` or calls return 500 errors. Parallel calls cause connection errors — always sequential.
23. **Do NOT use flow component tools on dashboards** — `add_components`, `update_component`, `replace_section_components`, `delete_components` target **flow layouts**. For dashboards use the `dashboard_`-prefixed tools: `add_dashboard_components`, `update_dashboard_component`, `replace_dashboard_section_components`, `delete_dashboard_components`.
24. **Dashboard draft lifecycle is explicit** — call `get_dashboard_draft_layout(dashboard_id)` first to get-or-create the draft and capture `draftId`, thread `draftId` through the component tools, then call `publish_dashboard_draft_layout(draft_id)` to land changes. To discard staged edits without deleting the draft, call `reset_dashboard_draft_layout(draft_id)` — the draft's content is rolled back to the published source. The published dashboard id only goes into `get_dashboard_draft_layout`; everywhere else pass `draftId`.
25. **Expressions in component properties go through `dynamicValue`** — `=` prefixes mathjs, `{$.foo}` interpolates a path, plain text is literal. `works` is not a free symbol; use `{$.works..fieldName}` or `{$.works:JSON}` (canonical count: `=count({$.works:JSON})`). See `references/dynamicValue.md`.
26. **Dashboard chart `*Key` properties take lodash dotted paths, not JSONPaths** — use `"data.courier"`, not `"$.courier"` (which dumps everything into an "Unknown" bucket). See `references/dashboards.md` § Chart & Metric-Card Pitfalls.
27. **Dashboard chart `tooltipFields[].value` is `dynamicValue`, not a field name** — use chart-context tokens (`{@options.category}`, `{@options.value}`) or mathjs aggregates. See `references/dashboards.md` § Shared Concepts.
28. **Data-grid computed columns use `column.value` with bare mathjs symbols** — `"=quantity * unitPrice"` (sibling column names resolve directly). `defaultValue`, `{@row.x}`, and `{quantity}` all silently render `0` in this context. See `references/layouts-and-components.md` § Computed Columns.
29. **Aggregated dashboards read different `*Key` properties than Works dashboards** — set `data_source` to `{"name": "Aggregate", "properties": {}}` to switch the render path; `total-by-bar-chart` aggregated reads `calculateStackKey` (no fallback), Works branch reads `calculateSeriesKey`. `reportData` is silently ignored in Works mode. Avoid `{"name": "data"}` or other custom names — they require an environment-side driver and otherwise 400 with no useful message. See `references/dashboards.md` § Dashboard Modes and § Setting the dashboard `dataSource`.
30. **A workflow dashboard with no `defaultQueryFilters` renders empty.** Without a recognized filter the works fetch is rejected upstream, `{$.works:JSON}` stays empty, and every tile shows `0` / `NO DATA`. Always pass `default_query_filters={"flowOriginId": ["<flow-guid>"]}` at `create_dashboard` time (or patch via `update_dashboard_metadata`). Recognized keys: `flowOriginId`, `currentState`, `displayName` (custom filterable flow properties also pass through). `currentState` values are the **only** valid strings `"Open" | "Closed" | "Completed" | "Deleted" | "Ok"`. See `references/dashboards.md` § `defaultQueryFilters`.
31. **Dashboard `dataPath` rules depend on mode.** *Works mode* (no `dataSource` or `dataSource.name == "works"`): the component must end up with `"dataPath": ""` — otherwise it scopes to a label-derived path (e.g. `$.countOfDeliveriesByCourier`) pointing at a non-existent field, so charts render `NO DATA` and metric cards render `0`. Caveat: `create_dashboard` / `add_dashboard_components` / `replace_dashboard_section_components` **also auto-derive an empty `""`** to that label path before the API sees it — so clear it afterward with `update_dashboard_component` (PATCH, the only tool that forwards `""` verbatim), or pre-supply a valid dotted path on the creating call (`references/dashboards.md` pitfall #12). *Aggregated mode* (any non-`works` `dataSource.name`, including custom drivers like `"AraDelivery"`): `""` is **also wrong here** — it makes `dynamicValue("", {data})` short-circuit to `""` so the component receives empty data and metric cards render `0`. Set `dataPath: "$"` (full response) or `"$.data"` (if the response is wrapped, see pitfall #42). See pitfalls #42–#45 below and `references/dashboards.md` pitfall #12.
32. **Seed empty-string `*Key` properties on chart components to match the schema's `OnNew` shape** — include `calculateSeriesKey: ""`, `calculateStackKey: ""`, `countSeriesKey: ""`, `tooltip: ""` on `total-by-bar-chart` (and equivalents on stacked / period / pie). Stacked / period-stacked charts also throw if `groupStackByKey` is missing — that key needs a real value, not empty. "NO DATA" rendering is almost always a `dataPath` issue (pitfall #31), not a missing `*Key`. See `references/dashboards.md` pitfall #13.
33. **`unitOfMeasure: undefined` renders the literal text `"undefined"` on bar charts** (Y-axis ticks + stack labels) because `${unitOfMeasure}` interpolates with no fallback. `null` renders `"null"`, `""` renders an empty suffix — only `undefined` produces the literal `"undefined"`. Metric cards are NOT affected (they use a ternary). For "no unit" on bar charts, set `"unitOfMeasure": " "` (single space) or `""`. See `references/dashboards.md` pitfall #14.
34. **`total-by-clustered-bar-chart` renders in Aggregated mode ONLY** — the SDK now ships a renderer, but only on the Aggregated path (dashboard `dataSource` set to `"Aggregate"` or a custom aggregate driver). On a Works-mode dashboard the chart still emits `null` and the tile renders blank — the calculations/Works path is explicitly "not supported yet". So: use it freely on Aggregated dashboards; on Works dashboards prefer `total-by-bar-chart`. Unlike the plain bar chart, the clustered chart's Aggregated path reads BOTH `groupSeriesByKey` (X-axis categories) and `groupStackByKey` (the clusters drawn side-by-side within each category), with the measure from `calculateStackKey ?? calculateSeriesKey`. See `references/dashboards.md` `total-by-clustered-bar-chart` section.
35. **Dashboard width `properties.width` is single-token only** — the backend regex on `BaseDashboardComponentPropertiesSchema.Width` is `^col-(?:[1-9]|1[0-2])$`, which rejects spaces. Per-breakpoint overrides like `"col-4 col-md-6"` fail API validation, and the older `sm-N`/`md-N` shorthand the SDK parser appears to handle (`col-sm-N`, not `sm-N`) can't reach the renderer. Use a single `col-N` and rely on the auto-derived responsive defaults.
36. **`grouped-metric-card` is the most mode-divergent component** — in Works mode `value` is a formula returning a `{label: number}` map; in Aggregated mode `value`, `valueLabel`, and `secondValue` are per-row `dynamicValue` expressions evaluated against each aggregated row. Authoring as if it's Works-mode on an Aggregated dashboard silently renders zero rows. See `references/dashboards.md` § `grouped-metric-card`.
37. **`heatmap-chart` has no Aggregated render path** — it always treats `data` as the works array. Putting a heatmap on an Aggregated dashboard (any non-`works` `dataSource.name`) yields a heatmap that tries to read `xAxis.valuePath` / `yAxis.valuePath` off aggregated rows. Heatmaps belong on Works-mode dashboards.
38. **`expandByDataPath` paths must be full from the work root, not relative to the expanded row.** Setting `expandByDataPath: "$.orderDetails.cart"` and then writing `dataPaths: ["$.quantity"]` or `groupBy.sourcePath: "$.model.displayName"` does NOT work. The engine replaces the array path with the current record in place but leaves the root structure unchanged, so paths must include the expand prefix: `dataPaths: ["$.orderDetails.cart.quantity"]`, `sourcePath: "$.orderDetails.cart.model.displayName"`. Same rule applies to `dynamicValue` tokens inside formula `dataPaths` and `condition`. Symptom of the bug: the report's `name` is absent from the response (`data.<reportName>` undefined) and the chart renders "No data" while other reports on the same dashboard work fine. See `references/dashboards.md` § `expandByDataPath` — flattening sub-arrays and pitfall #11.
39. **Layout schema changes don't migrate historical work data.** Moving a form field into a new section (e.g. `cart` → `orderDetails.cart`) means works created against the older flow version persist at the old path. A new report targeting the new path skips those works. Either accept the partial coverage, backfill the data, or be ready to fetch one historical work and check its actual top-level keys before assuming the form's current shape matches storage. See `references/dashboards.md` pitfall #12.
40. **`list_work` takes `flow_origin_id`, NOT the published `flow_id`.** Every other workflow tool (`create_work`, `get_flow_config`, `get_flow_steps`) takes the published version `id`. `list_work` is the exception — it filters by `flowOriginId` (the stable id shared across every version of the flow), because `flowId` changes on each publish and works pinned to older versions would otherwise drop out. Passing the wrong id kind silently returns `[]`. Both ids look like GUIDs; get the right one from `list_flows()` → `flowOriginId`. See `references/managing-work-items.md`.
41. **`reportData.properties` must list every path the report reads.** It drives the MongoDB projection. If `groupBy.sourcePath` is `$.paymentDetails.paymentMethod` and `properties` is only `["$.work"]`, the projection won't include `paymentDetails`, the group-by resolves to null on every work, and the chart collapses to a single `"Unknown"` bucket. The engine does NOT auto-derive `properties` from the rest of the report. The aggregator does union `properties` across all reports on the dashboard, but that "rescue" silently breaks when other reports change — always declare every path your own report uses (groupBy.sourcePath, fields[].dataPaths, condition token paths) in its own `properties` array. See `references/dashboards.md` § What `properties` actually does.
42. **The aggregate API response is wrapped in `{id, data: {values: [...]}, errors, ...}`.** The dashboard SDK passes this whole envelope to every component, so `$.values[...]` does NOT match at the root. Existing charts work via the `tryGetValueFromData` fallback that retries against `data.data` — but **only when the first lookup returns `undefined`**. Paths without `..` use `jsonpath.value` (returns `undefined` on miss → fallback fires → works). Paths with `..` use `jsonpath.query` (returns `[]` on miss → fallback does NOT fire → `:JSON` stores `[]` → `sum([])` = `0` silently). *How to apply:* either set `dataPath: "$.data"` on aggregated metric-cards so the formula's `$.values[...]` tokens resolve against the inner object, or rewrite tokens to `$.data.values[...]`.
43. **The `jsonpath` library does NOT support `&&`, `||`, or chained filters.** `[?(@.x == 'a' && @.y == 'b')]` returns `[]` silently (no error). `[?A][?B]` does not act as filter-then-filter — the second filter is ignored. Single-condition filters (`==`, `!=`) work; recursive descent (`..`) works. To match on multiple conditions, either restructure with `..` between filters, exploit redundancy in the data (e.g. when an "All" aggregate row equals the sum of per-key rows, `sum(matches)/2` isolates the aggregate value), or filter post-hoc in the per-row expression. Combined with pitfall #44, this is the most common cause of "metric card silently renders 0".
44. **`sum([])` and `sum(undefined)` silently return `0` in mathjs.** Combined with #42 (wrapper) and #43 (filter limitations), four distinct failure modes (empty dataPath, wrong dataPath scope, `..` + wrapped response, unsupported filter syntax) all surface as the same symptom — "the metric renders 0". When debugging, isolate by simplifying the formula: `"=42"` (does the card render at all?) → `"=count({$.values:JSON})"` (does the path see data?) → real formula. If the simple count works but the real formula renders 0, the filter is the issue.
45. **Aggregated `grouped-metric-card` `dataPath` must resolve to an array, or the component crashes with `.map is not a function`.** If `dataPath` ends in a filter expression (e.g. `…metrics[?(...)]`) and contains no `..`, `getValueByPath` calls `jsonpath.value` which returns only the FIRST match — a single object, not an array. The component then calls `.map()` on it and throws. *How to apply:* include `..` somewhere in the path (e.g. `$.data.values[?(@.group=='offer')]..metrics[?(@.labels.measure=='Sufficient offers')]`) to force `jsonpath.query`, which always returns an array.
46. **`list_*` for filtered queries** — If the user asks to find/search/filter works/flows/companies/assets by ANY condition (status, date, assignee, `data.*` field, etc.), use `search_works` / `search_flows` / `search_companies` / `search_assets` — NOT `list_work` / `list_flows` / `list_assets` + client-side filtering. The server has a real filter engine; iterating client-side is wasteful and ignores paging. See `references/advanced-search.md`.
47. **Missing `flowOriginId` on `search_works` / `search_assets` with `data.*`** — ANY `data.*` path in the request (`filter`, `sort`, OR `fields`) REQUIRES a sibling `flowOriginId` leaf under the same `and` group — `equals` for one flow / asset type, `in` for multiple. Without it the server returns 400. The only exception is the bare `"data"` projection key (no dot), which skips schema validation. Workflow: call `get_flow_data_schema(flow_origin_id)` first, then compose with BOTH leaves. `search_assets` follows the SAME `data.*` rules as Work (granular paths trim, bare `data` = whole doc); its one asset-specific quirk is shape-only — a requested-but-**absent** `data.*` path is omitted rather than materialized as `null`. See `references/advanced-search.md` (§ Asset Search) for wrong-vs-right examples.
48. **`fields` projection is opt-in via `enforce_fields=True`** — By default the server **ignores** `fields` and returns the resource's fallback projection (Always + Fallback whitelist entries). To actually apply the projection (and to surface any opt-in field — Work's `statusDisplay.*`, `data.*`, `comments`, every `assignedUsers.*` sub-path; Flow's `publishStatus`, `copiedFromId`, `environment`, `cardLayoutId`, `summaryCardLayoutId`, `template`, `hasRepeaterSection`, `blockChainEnabled`, `sequence`, `publishMode`, `resourceType`, `versionNumber`, `versionName`, `fromDate`, `toDate`) you MUST pass `enforce_fields=True` on the request. Setting `fields=[...]` alone has no effect; the response stays at the fallback shape. See `references/advanced-search.md` § "`enforce_fields` Behaviour".
49. **Over-specifying Object-root sub-paths in `fields`** — When projecting `statusDisplay` or `assignedUsers` on `search_works`, list the BARE ROOT KEY (`["statusDisplay"]`, `["assignedUsers"]`) — not each sub-path. The server dedupes sub-paths back to the root anyway, so enumerating them adds noise without changing the response. Pre-fix this also 400'd with "Path collision at statusDisplay.displayName"; post-fix the server silently collapses. (Different from `data.*` — granular `data.foo.bar` paths DO trim the payload because DataList projection is path-aware; `search_assets` trims the same way.) See `references/advanced-search.md`.
50. **Mixed-shape filter node** — Every filter node is exactly ONE of: a leaf condition (`field` + `operator` + `values`), an `and` group, or an `or` group. Mixing shapes — leaf + `and`/`or` children on the same node, OR both `and` + `or` populated on the same node — is rejected by the validator with 400. Wrap the leaf in an explicit `and` if you need conditions next to it: `{"and": [{leaf}, {other}]}`. Same applies to nesting — put the second group inside the first instead of putting both on one node. See `references/advanced-search.md` § "Leaf-XOR-group — one shape per node".
51. **`totalCount` is opt-in; `hasMore` is always populated** — Search responses carry `{items, page, pageSize, hasMore, totalCount}`. `hasMore` is **always populated** (use it as the primary "next page exists?" signal). `totalCount` is `null` by default — the server runs a cheap `pageSize + 1` probe instead of the full `$facet + $count` aggregation. Pass `include_total_count=True` to get the exact total (slower). See `references/advanced-search.md` § "Counts & pagination".
52. **Soft-deleted records hidden by default** — `search_works`, `search_assets`, and `search_flows` exclude tombstoned records by default. Work / Asset: `status = "Deleted"` is excluded unless the caller's filter mentions `status` anywhere on the AND-spine (the root leaf or any branch inside an `and` group — even `status != "Open"` or `status in [...]` counts). Flow: same rule for `state in ["Deleted", "Archived"]`. A `status`/`state` reference that lives **only inside an `or` branch** does NOT trigger opt-out — the soft-delete guard still applies. To explicitly include deleted records, add the status/state leaf on the AND-spine (`status = "Deleted"`, `state in ["Active", "Deleted"]`, etc.). See `references/advanced-search.md` § "Default soft-delete exclusion".
53. **Range operators are number/date only** — `greaterThan`, `greaterThanOrEqual`, `lessThan`, `lessThanOrEqual`, and `between` are rejected on **string** fields (returns 400 from the validator). Use them on dates (`lastModified`, `created`, `data.*` date paths) and numbers (`data.*` number paths). String fields support `equals`/`notEquals`/`in`/`notIn`/`startsWith`/`exists`/`notExists` on every resource; `contains`/`endsWith` are **Flow-only** (rejected on Company/Work/Asset and on all `data.*` strings — see pitfall #55). See `references/advanced-search.md` § operator matrix.
54. **Empty `contains` / `startsWith` / `endsWith` rejected** — Passing empty or whitespace-only `values` with `contains`, `startsWith`, or `endsWith` returns 400 from the validator. Previously this silently produced a match-everything regex (e.g. `contains: ""` matched every document). Trim caller input and reject empties on the client side too, or use `exists`/`notExists` if "any/no value" is what you actually want.
55. **`contains` / `endsWith` are Flow-only** — Accepted only on `search_flows` string fields. They are rejected with 400 on `search_companies`, `search_works`, and `search_assets` (whitelist) strings AND on **all** `data.*` STRING paths (unanchored/trailing-anchored regex is non-indexable on dynamic fields; the non-Flow resources disallow them outright). The portable string operators are `equals`/`notEquals`/`in`/`notIn`/`startsWith`. The simple GET `name*`/`*name` wildcard form is a separate, non-operator-gated path and still works on `data.*` strings. See `references/advanced-search.md` § operator matrix.

56. **eventName uniqueness is FLOW-wide** — the engine keys event idempotency per work item by `eventName`; a duplicate anywhere in the flow causes runtime 403s that stick work items. `manage_action` validates this before writing and `action="replace"` keeps the action GUID stable while reshaping it.
57. **Nested dict PATCH deep-merge keeps omitted keys** — to DELETE a nested key on a component, call `update_component(..., unset=True)` with that key, or `skip_merge_properties=True` to replace the whole `properties` object. Several components at once: `batch_update_components` (sequential, per-item results).
58. **Secret values are write-only** — integration responses never echo parameter values or ciphertext; verify secret changes by behaviour (`test_integration_endpoint`), not by reading them back.
59. **CSV exports: scalars via `$.data.<field>`; a data-grid needs expandable columns + a `[*]` shard + a BARE filter token.** Form fields live under `data.*` → author `$.data.<field>` (a bare `$.<field>` only hits work-root `workCode`/`status`/`statusDisplay.displayName`). Scalars need no column. **A data-grid unwinds into one row per element only if BOTH:** (1) it's registered as **expandable work-grid column(s)** — `manage_columns add` with `isExpandedProperty:true` + `valuePaths:["$.<grid>[{$.index}].<sub>"]` (this is what exposes the grid to the export; a couple of columns expose the whole element — without any, every per-element cell is blank); **and** (2) the export uses shard `$.data.<grid>[*].id` (bracket-star) + per-element fields `$.data.<grid>[?(@.id == $.shards.<key>)].<sub>` with a **bare** `$.shards.<key>` — NOT the quoted/braced `'{$.shards.<key>}'`, which never matches. `shardConfigs` are array-unwinds (cross-product), not entity joins. Dates: `dataType:"Date"` + `$.data.<field>`. Never pass `export` to `update_flow_properties`; `publish_flow` commits it (a `list` on the origin id can read stale right after). See `references/exports.md`.
60. **Auto-populating a field from a selected asset uses `defaultValue` + `recalculateDefaultValueWhenDataPathChange`, NOT `autoPopulate`.** There is no `autoPopulate` property — a `{from, to}` array on a `search-things` picker is silently ignored, so a flow can *look* configured yet copy nothing. To push a value from an asset picked in a `search-things` (dataPath `$.cmo`) into another field, set on the **target** field: `defaultValue: "$.cmo.data.<assetField>"` AND `properties.recalculateDefaultValueWhenDataPathChange: ["$.cmo"]`. Three silent traps: (a) the asset's own fields live under `.data`, so the path is `$.cmo.data.sites`, NOT `$.cmo.sites`; (b) recalculation only fires when `defaultValue` is a dynamic expression (starts with `$.`, `=`, or `{$.`) — an empty or literal `defaultValue` disables it, so `defaultValueDataKey` alone (with a blank `defaultValue`) does nothing; (c) the field must actually be present in what the picker stored — leave the picker's `dataPaths` unset/`null` (default returns the full asset object) or include the field if you set `dataPaths`. See `references/layouts-and-components.md` § Populating a Field from a Selected Asset.
61. **Multiple `fields[].dataPaths` are first-found COALESCE, not summed.** The engine walks the list per (expanded) row and uses the first path that resolves, then stops — so listing two paths does NOT add them (to sum two fields use one `=`-formula entry, `"={$.a}+{$.b}"`). Use it to chart one measure that different works store under different paths (schema divergence / array-vs-scalar): a work matching either path feeds the same `operations`. Caveats: declare every alternative in `properties`, and each missed path still logs a harmless per-work `"Data path '<path>' not found in data."` before falling through (the value is still correct). To suppress that noise, use two same-`targetPath` fields gated by `fields[].condition` (a false condition skips silently and they still merge). See `references/dashboards.md` § Multiple `dataPaths` — first-found coalesce.
62. **Card `cardConfig` dataPath slots must resolve to a scalar leaf — never a bare reference/array field.** A card renders `title`, `subTitle[]`, `statusText`, `secondaryValue`, and `items[].value` by resolving each as a dataPath against the work. A `search-things`/entity-reference field resolves to the WHOLE object `{id, displayName, imageUrl, data, …}` (same shape as #60 / `references/layouts-and-components.md` § search-things), and an array to a list. **Two slots hard-crash the ENTIRE board** on a non-scalar — thrown during render with no card-level error boundary, so one bad card is a full-view outage: `statusText` (status-pill label, rendered **raw** → **React error #31** "Objects are not valid as a React child") and `statusClassName` (status-pill color, tested with `.includes('#')` → **`TypeError: value.includes is not a function`**). The other slots (`title`, `subTitle[]`, `secondaryValue`, `items[].value`) coerce a non-string to `---`/blank — no crash, but silently wrong. Always append the scalar leaf: `$.newOpportunity.opportunityType.displayName`, NOT `$.newOpportunity.opportunityType`. ACL trap: it only fires for users whose visible set includes a work item where the field is populated as an object (legacy rows storing a plain string render fine), so it slips past casual testing. Edit via `manage_card_layout(action="update")` on a draft (deep-merges — send only the changed slot); `publish_flow` commits it. See `references/card-layout.md`.
63. **Duplicate-work data control lives in `flowFeatures.createAndDuplicateWork.duplicate` — edit on a DRAFT, whole-object write.** To control which fields the DIANA **Duplicate** button carries, set `flowFeatures.createAndDuplicateWork.duplicate {enabled, includePaths, excludePaths}` — `includePaths` (whitelist, `["$"]` = all) applied first, then `excludePaths` removed; allow-all-minus is `includePaths:["$"]` + `excludePaths:[…]`, paths are `$.<field>` from the work-data root. Four traps: (a) **a write to a *published* flow is silently dropped** — do `create_flow_draft` → `update_flow_properties(draftId, …)` (expect `changed:[flowFeatures]`, not `changed:[]` + `dropped_property`) → `publish_flow` → re-resolve id via `list_flows`; (b) **`get_schema` never surfaces this** (it's a `flowFeatures` sub-key) — `references/managing-flows.md` § Duplicate & Create Work is the source of truth; (c) the component flags **`copyData`/`cloneData` are inert decoys** — no runtime reads them; (d) `update_flow_properties` **replaces the entire `flowFeatures` object** (no deep-merge) — read-modify-write via `get_flow_config(id, path="properties.flowFeatures")` (note: read path is `properties.flowFeatures`, write body is bare `flowFeatures`) or you clobber siblings (`leftPanel`, `calendarBoard`, …). Verify from MCP with `duplicate_work(sourceWorkId)` → `get_work(newWorkId)`. **All verified end-to-end on a test ecosystem.**
