# Troubleshooting

Symptom → cause → fix for every known Rise-X MCP failure mode.

A bare `Pitfall #N` below refers to `references/common-pitfalls.md`; a reference
that names a file (e.g. "Pitfall #14 in `references/dashboards.md`") uses that
file's own independent numbering.

| Error | Cause | Fix |
|---|---|---|
| 403 Forbidden on edit/publish | Using original ID after drafting | Use the draft ID returned by `create_flow_draft` or `create_layout_draft` |
| 403 on component edit | Layout is Published, not Draft | Check layout `publishStatus` via `get_layout`; call `create_layout_draft(layoutId, draftFlowId)` if Published |
| "Cannot connect to host" | Transient network error | Retry the same call |
| "Step not found" / 404 on `get_flow_step` | Using `stepId` or `taskId` instead of the record `id` | Use the `id` field from `get_flow_steps`. (`manage_action`, `manage_task_invites`, `delete_step`, `rename_step` accept any of the row's GUIDs and resolve them — `get_flow_step` is the read that still wants `id` specifically.) See `references/building-workflows.md` § ID mapping. |
| `validation` error with a `steps:` listing | Step tool got a GUID that matches no step row | Pick the right step from the listed `{id, stepName, stepDisplayName}` — no need to re-fetch |
| 403 on `create_asset` | A flow id (or stale id) passed instead of `flowOriginId` — NOT a permissions problem | Get the `flowOriginId` from `search_flows` (flowResourceType=Entity) or `list_asset_types` (the error hint says this too) |
| 403 "is in 'Deleted' mode" on edit/draft | The flow id belongs to a deleted or superseded version (re-publish issues a new id) | Call `list_flows` and use the current live id; `flowOriginId` is stable across republishes. **Worse trap:** a superseded id can also ACCEPT writes (200 + `changed`) — they land on the dead version and never appear in the live flow. Re-resolve the id from the publish envelope or `list_flows` after every publish |
| Components vanish after publish | Called `publish_layout` before `publish_flow` | Never call `publish_layout` — only use `publish_flow`, which auto-publishes linked layouts |
| Empty layout after publish | Called `create_layout_draft` on a new (never-published) flow | Don't call `create_layout_draft` on new flows — use `layoutId` from `get_flow_steps` directly |
| "Ecosystem not set" (`no_ecosystem` code) | No active workspace | Call `set_active_ecosystem("name")` first |
| `update_component` returns 400 but the hint says it may have committed | Known API quirk on advanced data-grid patches | Follow the hint: `get_layout(id, format='components')`, inspect, only retry if the write is absent |
| `validation` error naming a manage_* tool | Sub-resource key sent to `update_flow_properties` | Use the named tool (`manage_pipeline`, `manage_export`, `manage_chain`, `manage_card_layout`, `manage_related_flow`) |
| Empty `list_work` and you don't know why | Wrong user, wrong ecosystem, or no data | `whoami()` shows the bound user + ecosystem; check role/company visibility |
| Duplicate column 400 error | Column with same `key` already exists | Call `manage_columns(flow_id, "list")` first; use `manage_columns(flow_id, "update", ...)` instead |
| Dashboard chart renders "NO DATA" | Auto-derived `dataPath` (e.g. `$.countOfDeliveriesByCourier`) OR wrong `*Key` path (`$.foo` instead of `data.foo`) OR wrong `defaultQueryFilters` | Set `"dataPath": ""`; use lodash dotted-path form for `*Key` properties; verify `currentState` filter values. Pitfalls #12, #1 in `references/dashboards.md` |
| Every tile on a brand-new dashboard renders `0` / `NO DATA` | `defaultQueryFilters` is empty / unset, so `{$.works:JSON}` is empty | `update_dashboard_metadata(id, default_query_filters={"flowOriginId": ["<flow-guid>"]})`. Pitfall #30 |
| Bar / stacked / period chart shows `<number> undefined` on labels and Y-axis | `unitOfMeasure` is `undefined` (key missing) — the chart template interpolates without fallback | Set `"unitOfMeasure": " "` (single space) or `""`. Pitfall #14 in `references/dashboards.md` |
| Stacked-bar chart throws / renders an error boundary | `groupStackByKey` is missing — the SDK calls `throwIfNoRequiredPropertiesForStackedChart` | Add a real `groupStackByKey` value (not empty string). Pitfall #13 in `references/dashboards.md` |
| `total-by-clustered-bar-chart` renders blank | Used on a **Works-mode** dashboard — the clustered chart only has an Aggregated renderer; the Works path emits `null` | Put it on an Aggregated dashboard (`dataSource: {"name": "Aggregate", ...}`), or switch to `total-by-bar-chart` for Works mode. Pitfall #34 |
| `grouped-metric-card` renders zero rows on an Aggregated dashboard | `value` authored as a Works-mode `{label: number}` formula on a layout with `dataSource.name: "Aggregate"` | Switch to per-row mode: set `valueLabel`, `value`, and (optional) `secondValue` to `dynamicValue` expressions on the aggregated row's `targetPath`s. Pitfall #36 |
| Aggregated dashboard returns 400 with a generic "Object reference not set to an instance of an object." or similar message | `dataSource.name` is `"data"` (or any other custom string) on an environment that doesn't have a matching driver | `update_dashboard_metadata(id, data_source={"name": "Aggregate", "properties": {}})`. See `references/dashboards.md` § Setting the dashboard `dataSource` |
| Expand-based chart renders "No data" while sibling reports on the same dashboard show data, and the report's `name` is absent from `data` in the aggregate response | `groupBy.sourcePath` / `fields[].dataPaths` use the relative form (e.g. `"$.quantity"`) instead of the full path including the expand prefix (e.g. `"$.orderDetails.cart.quantity"`) | Rewrite the report paths to be full from the work root. Pitfalls #38 in `references/common-pitfalls.md` and #11 in `references/dashboards.md` |
| Expand-based chart only shows recent orders and ignores historical works | The form's section structure changed across flow versions; old works persist under different paths than new ones | Verify by inspecting a historical work's top-level keys vs. the form layout. Backfill or accept the partial coverage. Pitfalls #39 / #12 |
| Group-by chart collapses every row into a single `"Unknown"` bucket (legend shows only "Unknown") | The `groupBy.sourcePath` field isn't declared in the report's `properties` array, so MongoDB doesn't project it and the engine sees null on every work | Add the groupBy path to `properties` (e.g. add `"$.paymentDetails.paymentMethod"` to a payment-method pie's `properties`). Pitfall #41 |
| `list_work` returns `[]` even though works exist for the flow | Passed the published `flow_id` instead of `flow_origin_id` — only `flowOriginIds` is applied by the v3 data-grid filter, and a flow-id value won't match | Pass `flowOriginId` from `list_flows()` or from a work's `flowOriginId` field. Pitfall #40 |
| Section's children render with no padding / `col-N` stacks full-width with no gaps | Section is missing `properties.useContainer: true`, so no `<Grid container>` wrapper is emitted and percentage widths can't compose | Set `useContainer: true` in the section's `properties` when calling `add_dashboard_components` or `create_dashboard`. See Container Pitfall #2 in `references/dashboards.md` |
| Metric card on Aggregated dashboard renders `0` (units like `MT` / `%` still show) | One of four causes, all silent: (a) `dataPath: ""` makes `dynamicValue("",…)` short-circuit; (b) API response is wrapped in `{data: {values:…}}` and tokens use `$.values[…]` against the root; (c) JSONPath uses `..` so empty-match returns `[]` and `tryGetValueFromData`'s fallback doesn't fire; (d) filter uses `&&`/`||`/chained `[?A][?B]` which jsonpath doesn't support | Set `dataPath: "$"` or `"$.data"` matching the wrapper. Simplify formula to `"=42"` to confirm card renders, then `=count({$.values:JSON})` to confirm path. Rewrite `&&` filters to single-condition + `..` or arithmetic tricks. Pitfalls #31, #42, #43, #44 |
| `grouped-metric-card` throws `.map is not a function` in console | `dataPath` ends in `[?(…)]` with no `..` in the path, so `getValueByPath` uses `jsonpath.value` and returns one object instead of an array | Add `..` to the path (e.g. `$.data.values[?(@.group=='offer')]..metrics[?(@.labels.measure=='Sufficient offers')]`). Pitfall #45 |
| Workboard blank / "Unexpected Application Error" in console (React #31, or `TypeError: value.includes is not a function`) | A card `cardConfig.statusText` or `statusClassName` points at an object/array field — e.g. a `search-things` reference resolving to `{id, displayName, imageUrl, data}` | Append a scalar leaf (`.displayName`) via `manage_card_layout(action="update")` on a draft, then `publish_flow`. `statusText` (raw render → React #31) and `statusClassName` (`.includes` → TypeError) both crash the whole board; other slots silently show `---`. Only users who can see a card with that field populated hit it. Pitfall #62. See `references/card-layout.md` |
